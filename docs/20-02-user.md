# User manual

Use `tool.scad-project` for maintained SCAD repositories that need shared
configuration, design documentation, Build, Verification, publication and
release workflows.

## Consumer structure

A current-generation consumer normally has:

```text
project.yml
project.scad.yml

tools/tool.git-project
tools/tool.scad-project

bootstrap.ps1 / bootstrap.sh
update.ps1 / update.sh

.github/workflows/self-ci.yml
.github/workflows/self-release.yml      # when releases are published
.github/workflows/self-pr-cleanup.yml   # when PR previews are published
```

Generic root launchers come from `tool.git-project`. SCAD owns only its
post-update synchronization hook and domain behavior.

## Version selection

The maintainer selects the released `tool.scad-project` ref in `project.yml`.
The committed gitlink records the exact resolved revision.

After running the generic updater, the SCAD post-update hook aligns released
SCAD reusable-workflow refs to the same semantic tool release.

## Main commands

Typical commands include:

```text
scad-project config-lint
scad-project tooling-check
scad-project docs-lint
scad-project design-lint
scad-project design-build
scad-project build
scad-project verify
scad-project build-audit
scad-project build-index
```

The root [README](../README.md) gives the detailed current command/configuration
examples.

## Build/verification model

Normal maintained repositories expose only the SCAD capabilities they actually
have:

```text
scad.docs
scad.build
scad.verify
```

The reusable CI architecture is documented in
[40-11-ci-workflow.md](40-11-ci-workflow.md).
